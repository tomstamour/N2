# Chasing the Ask to Fill Long Entries on IBKR's TWS API (ibapi): An Implementation Guidance Summary

## TL;DR
- **Build a single-client, event-driven "chase-the-ask" engine** that subscribes to streaming Level-1 data via `reqMktData` (ASK tick type = 2), maintains a state machine over one working BUY LMT order, and re-prices it in place with `placeOrder` using the SAME `orderId` whenever the ask moves materially — never canceling-and-replacing.
- **The single biggest risk is not the code but IBKR's pacing/efficiency limits**: the hard 50 messages/second API cap and the Order Efficiency Ratio (OER = (submissions+revisions+cancels)/(executions+1)). IBKR's "Order Management Overview" states "An OER above 20 is generally considered excessive and indicative of inefficient order management logic. Clients who routinely report an OER above 20 will receive notification," and an Elite Trader field report relays being "told that OER over 50 was a hard cutoff, on a daily basis." Throttle modifications to a few per second, only re-price on *meaningful* changes, and seriously evaluate IBKR's native **Relative/Pegged-to-Primary (REL)** order, whose internal repricing is NOT counted against your OER.
- **Track fills with `orderStatus` (cumulative `filled`/`remaining`) and keep `totalQuantity` at the ORIGINAL size when modifying a partially-filled order** — do not resend "remaining," or you will under-buy. Enforce the Cap as a hard ceiling on the computed limit, set `outsideRth=True`, and use only LMT (market orders are rejected in ETH).

## Key Findings

**1. `reqMktData` is sufficient for chasing the ask, and is the correct choice given the constraint.** IBKR's documentation states top-of-book data from `reqMktData` "is not tick-by-tick but consists of aggregated snapshots taken at intra-second intervals," and per IBKR's TWS API "Top Market Data (Level I)" frequency table that interval is **250 ms for "Stocks, Futures and others"** (US Options 100 ms; FX pairs 5 ms). The ASK price arrives in the `tickPrice` callback with `tickType == 2` (ASK), with a paired `tickSize` (tickType 3) following. Use **streaming** mode (`snapshot=False`), not snapshots: a snapshot returns data once and then a `tickSnapshotEnd` ~11 seconds later, useless for continuous chasing. The 250 ms cadence is a real limiter — you cannot see every print of a fast mover, and practitioners note delivery is "bursty" (you may get nothing for a moment, then a burst of updates). For a press-release momentum spike this is acceptable because you are chasing the *displayed ask*, not trying to read every trade; but it means your information is up to ~250 ms stale, which is precisely why an offset above the ask is needed. The reason to prefer `reqMktData` over `reqTickByTickData` is legitimate: tick-by-tick subscriptions consume from the same limited pool as market-depth lines (governed by the depth/lines formula), whereas Level-1 streaming lets you run more concurrent symbols/clients.

**2. Single-client architecture is the IBKR-recommended model and works cleanly here.** One `EClient`/`EWrapper` pair connects to TWS/IB Gateway; the `EReader` thread reads the socket and enqueues messages, and the API's message-processing loop dispatches them to your callbacks. Market-data callbacks (`tickPrice`/`tickSize`) and order callbacks (`nextValidId`, `openOrder`, `orderStatus`, `execDetails`, `error`) all arrive on the **same single processing thread**, so your chase logic runs in one place with no cross-thread locking needed — provided you do all state mutation and `placeOrder` calls from within that callback thread. Critically: you must wait for the `nextValidId` callback (which also signals the connection handshake is complete) before sending any requests, and use that integer as your starting `orderId`. Modification requires the connection use the **same client ID** that placed the order (or client ID 0 with binding for orders placed elsewhere/manually).

**3. Modify-in-place is correct and materially faster than cancel/replace — and IBKR explicitly endorses it for efficiency.** Per IBKR's TWS API "Modifying Orders" doc: "The function IBApi.EClient.placeOrder can then be called with the same fields as the open order, except for the parameter to modify. This includes the IBApi.Order.OrderId, which must match the IBApi.Order.OrderId of the open order. It is not generally recommended to try to change order fields aside from order price, size, and tif." So changing only **price, size, or tif** is supported and recommended; changing other fields should use cancel/new instead. IBKR's "Considerations for Optimizing Order Efficiency" states: "logic which acts to cancel and subsequently replace orders should be substituted with logic which simply modifies the existing orders. This will serve to reduce the process from two order actions to a single order action, thereby improving the OER." So modify-in-place both lowers latency (one message vs two) and halves the OER impact per re-price.

**Important caveat on queue priority:** A price modification that makes a resting limit order more aggressive (raising a buy limit) generally loses time priority at the new price level anyway, because you are joining the back of the queue at the higher price — this is exchange mechanics, not an IBKR artifact. (Separately, the docs note that the API *binding* process for taking over manual/other-session orders currently cancels/resubmits on the exchange, affecting queue position; this applies to binding, not to ordinary same-client modifications.) For a chase strategy this is largely moot: you are deliberately moving up to take liquidity, not waiting in a queue.

**4. The Cap is best enforced two ways simultaneously — in your code AND on the order.** Compute `target = min(ask + offset, cap)`. Your code should refuse to send any limit above `cap`. Additionally, because a plain LMT's limit price already acts as a ceiling (a BUY LMT never fills above its limit), setting the limit at-or-below the cap gives a broker-side guarantee. The decision when `ask + offset > cap` is a policy choice: (a) **rest at the cap** (leave a working LMT at the cap so you still fill if the ask ticks back down — usually best for "fill what I can up to my max price"), (b) **pause** chasing and resume if the ask drops back into range, or (c) **stop/cancel** if you only want fills strictly tracking the live ask. Resting at the cap is the most common and is effectively free in OER terms once placed (no further modifies while ask is above cap).

**5. Partial fills: keep `totalQuantity` at the ORIGINAL size when modifying.** This was verified specifically. When a working BUY LMT (e.g., 1,000 shares) is partially filled (say 300 done, 700 remaining) and you re-price by calling `placeOrder` with the same `orderId`, **`Order.totalQuantity` must remain the original 1,000** — IBKR tracks the filled portion internally against the order's `permId`. If you instead send `totalQuantity = 700`, IBKR interprets 700 as the new cumulative target (of which 300 is already done), so the order works only 400 more shares and you **under-buy by 300**. The invariant, confirmed in the ib_insync/ib_async source (`remaining = totalQuantity − filled`), is **`totalQuantity = filled + remaining`** at all times. The `orderStatus` callback's `filled` and `remaining` fields are **cumulative over the order's lifetime** (not per-fill); `execDetails`/`Execution.cumQty` gives the same cumulative number, while `Execution.shares` is the size of the individual fill. A reader comment on an IBKR Campus article claiming "resubmitting the order would, in fact reset any filled quantity to 0" is an unendorsed third-party remark and is incorrect for a genuine same-`orderId` modify; only submitting under a NEW orderId starts fresh at filled=0.

**6. ETH/RTH handling is straightforward but has hard rules.** Set `Order.outsideRth = True` to allow the order to work in pre-market (4:00–9:30 ET) and after-hours (16:00–20:00 ET). **Only limit-type orders work in extended hours — MKT and STP are rejected/inactive outside RTH**, so your LMT-based chase is inherently ETH-compatible. Note that IBKR's *overnight* session (an emerging, separate venue, ~20:00–03:50 ET) is treated as an independent venue with its own TIF (`Overnight`/`Overnight+Day`) and only supports Limit and Adaptive order types; `outsideRth` alone does not route there. ETH books are thin with wide spreads, so your offset and cap logic matter even more, and the 250 ms data combined with a fast PR spike in a thin book can produce large slippage if the offset is too aggressive.

**7. Pacing and OER are the real constraints — design around them.** Two distinct limits:
- **Message rate:** Per IBKR's TWS API "Order Limitations" page, "the TWS API's inherent limitation of 50 messages per second implying a maximum of 50 orders per second being sent to the TWS"; IBKR's RTD troubleshooting doc adds that "If the 50 messages/second rate is exceeded, TWS will eventually close the connection." Exceeding it triggers error code 100 ("Max rate of messages per second has been exceeded"). Each `placeOrder` modify is one message; at a few re-prices/second per symbol you are far under, but a multi-symbol PR scanner firing simultaneously can approach it.
- **Order Efficiency Ratio:** `OER = (Order Submissions + Order Revisions + Order Cancellations) / (Executed Orders + 1)`. IBKR's "Order Management Overview" states "An OER above 20 is generally considered excessive and indicative of inefficient order management logic. Clients who routinely report an OER above 20 will receive notification," and an Elite Trader thread relays "That warning was for an account with several thousand place/edit/cancels per day. I was also told that OER over 50 was a hard cutoff, on a daily basis." Crucially, **modifications count as Order Revisions and DO add to OER**, but IBKR's "Considerations for Optimizing Order Efficiency" says that "as the revision logic embedded within IB-supported order types is not considered an order action for the purposes of the OER, consideration should be given to using IB order types, whenever practical." This is the strongest argument for the Relative/Pegged-to-Primary alternative below.

**8. A native IBKR order type may do the whole job with one message and zero OER cost: Relative / Pegged-to-Primary (`REL`).** IBKR's `REL` order "derives its price from a combination of the market quote and a user-defined offset" and "is submitted as a limit order and modified according to the pricing logic until it is executed" — and "you can also set an optional price cap." In API terms: `order.orderType = "REL"`, `order.auxPrice = offset`, `order.lmtPrice = priceCap`. **However**, a standard Relative BUY pegs to the National Best *Bid* + offset (it is designed to *post* liquidity aggressively, not to lift the offer), so it is not a literal "ask + offset" taker. For genuinely chasing/lifting the ask, **Pegged-to-Market (`PEG MKT`)** computes "Buy order price = Ask price − offset" with a limit price as the worst acceptable price — closer to the intended behavior, though availability/routing is more restricted. The tradeoff: native pegs offload repricing to IBKR (no OER, no 250 ms client loop, no message-rate exposure) but give you less precise control over *exactly* how and when the price moves, and some peg types have exchange/ETH restrictions. The custom `reqMktData` + modify loop gives full control at the cost of OER/pacing management. **Recommendation: prototype both; prefer the native peg if its fill behavior meets the goal, fall back to the custom chase when you need bespoke offset/cap/throttle logic.**

## Details

### Architecture and event/callback flow
1. **Connect** and capture `nextValidId(orderId)`; store as `next_order_id`. Also handle `managedAccounts` and `error`.
2. **Subscribe** to the symbol with `reqMktData(reqId, contract, "", False, False, [])` for streaming top-of-book. Map `reqId → symbol/state`.
3. **`tickPrice(reqId, tickType, price, attrib)`**: when `tickType == 2` (ASK), update `state.last_ask = price` and the timestamp, then call the **re-price evaluator**. (Optionally also watch tickType 4 = LAST and 1 = BID for sanity/spread logic.) Respect `attrib.pastLimit`/`canAutoExecute` if you want to gate on quote validity.
4. **`orderStatus(orderId, status, filled, remaining, avgFillPrice, permId, ...)`**: update `state.filled`, `state.remaining`, `state.status`. On `status == "Filled"` (remaining == 0), tear down (cancel `reqMktData`, mark complete).
5. **`openOrder` / `execDetails`**: reconcile; `execDetails` gives authoritative per-fill data (`cumQty` cumulative, `shares` this fill).
6. **`error(reqId, code, msg, ...)`**: handle 100 (rate), 201/202 (reject/cancel), 10147/10148 (cancel of not-found/already-filled), 104/105/161 (modify/cancel-state issues). Treat these as state-resync triggers.

### State machine (per symbol)
- `IDLE` → `ARMED` (got valid ask) → `WORKING` (order live) → `WORKING_PARTIAL` (filled>0, remaining>0) → `DONE` (remaining==0) or `CAPPED` (resting at cap, ask above cap) or `ABORTED` (error/timeout/stop).
- Single working `orderId` per symbol at a time; never have two live chase orders for the same target.

### Offset, re-pricing, and anti-thrash logic
- **Offset choices:** fixed cents (simplest, e.g., +$0.02–$0.05), a number of ticks, a fraction of the current spread (e.g., ask + 25% of spread), or a percentage of price (better for high-priced names). For thin ETH books, spread-based or tick-based offsets adapt better than a fixed penny value.
- **Compute** `target = round_to_tick(min(ask + offset, cap))`. Buy-side rounding should round DOWN to a valid increment to avoid sub-penny rejects (sub-$1 names have $0.0001 increments; ≥$1 names use $0.01).
- **Re-price gate (debounce/hysteresis):** only modify if ALL hold: (a) `target` differs from the current working limit by at least a minimum delta (e.g., ≥1 tick or ≥ offset/2) — this is the key anti-thrash rule; (b) at least `T` milliseconds have elapsed since the last modify (a token-bucket/throttle, e.g., max 3–5 modifies/sec/symbol); (c) the order is in a modifiable state. IBKR's OER guidance explicitly says an order modification based on a price change should only be triggered if the prior price is no longer competitive and the new suggested price is competitive, and to avoid modifications that do not substantially increase the likelihood of the order interacting with the NBBO.
- **Aggressiveness tradeoff:** larger offset → higher fill probability but worse average price and more slippage on spikes; smaller offset → better price but you lag a fast ask and may never fill. The cap bounds the worst case regardless.
- **Don't chase downward needlessly:** for a pure "get filled" goal, when the ask falls you can leave the limit where it is (it becomes more marketable) to save an OER revision — only move up. Move down only if you also want to avoid overpaying as the ask retreats.

### Modify-in-place loop (the core)
- Maintain one mutable `Order` object per symbol. To re-price: set `order.lmtPrice = target`, keep `order.totalQuantity = ORIGINAL_QTY`, keep `order.action="BUY"`, `order.orderType="LMT"`, `order.outsideRth=True`, `order.tif="DAY"` (or `GTC`), then `placeOrder(same_orderId, contract, order)`. Do NOT increment the orderId for a modify.
- Because `placeOrder` is **fire-and-forget (asynchronous)** — there is no synchronous ack — treat the modify as a *request*, not a confirmed state change. Update your "intended limit" immediately but only treat the order as actually at that price when `openOrder`/`orderStatus` confirm. Keep a `pending_modify` flag and the last-sent limit to detect drift.

### Partial-fill bookkeeping
- Source of truth for filled quantity is `orderStatus.filled` (cumulative) / `remaining`. Reconcile against summed `execDetails.shares` if you want belt-and-suspenders.
- When modifying after a partial fill: resend `totalQuantity = ORIGINAL_QTY`. Never compute and send "remaining" as the new total.
- If you ever need to *reduce* size, ensure the new `totalQuantity` is ≥ already-filled; sending a total ≤ filled is at best a no-op/complete and at worst rejected (the exact error code is not authoritatively documented — validate in paper). `totalQuantity = 0` is an explicit error.

### Cap enforcement
- Hard ceiling in code: `target = min(ask+offset, cap)`; assert `target ≤ cap` before every send.
- When ask runs above cap: default to **rest at cap** (place/keep LMT at cap, stop modifying) so you still capture fills if it pulls back; optionally cancel if "track the live ask only" is the requirement. Resting and ceasing modifications is also the OER-friendly choice.

## Recommendations
1. **Stage 1 — Prototype the native peg first.** Implement a `PEG MKT` (or `REL` if posting-style behavior is acceptable) BUY with `auxPrice=offset` and `lmtPrice=cap`, `outsideRth=True`, `totalQuantity=target_shares`. Measure fill quality on a few live PR movers in paper and (small size) live. If fills are acceptable, **you are done with near-zero OER/pacing risk** because IBKR does the repricing. Benchmark to beat: fill rate of intended shares and average fill price vs. your cap.
2. **Stage 2 — Build the custom `reqMktData` + modify-in-place chase** only if you need bespoke control (custom offset curves, multi-symbol prioritization, spread-adaptive logic). Implement the single-client callback architecture, the per-symbol state machine, and the debounce + throttle gates from day one.
3. **Instrument OER and message rate from the start.** Log every submission/revision/cancel and every execution; compute a running daily OER and alert if it approaches 20 (IBKR's stated "excessive" threshold). Implement a global token bucket well under 50 msg/sec (e.g., cap at 30–40 to leave headroom for market-data and other traffic). **Threshold to change behavior:** if OER trends >20 or you see error 100, widen the re-price delta, lengthen the throttle interval, reduce symbols traded concurrently, or switch that symbol to a native peg.
4. **Tune offset/throttle empirically.** Start conservative: offset = 1–2 ticks (or ~0.1–0.2% for higher-priced names), throttle = max ~3 modifies/sec, re-price delta ≥ 1 tick. Loosen offset only if fill rate is too low; tighten throttle if OER/pacing pressure appears.
5. **Always paper-trade the full flow first**, including partial fills and the modify-after-partial path, to confirm `totalQuantity` semantics and capture the exact error codes your TWS build emits. Note IBKR paper does NOT support REL/peg fills realistically, so validate peg behavior with small live size.
6. **Build robust teardown:** on `Filled`, `Cancelled`, or fatal error, cancel the `reqMktData` line and clear per-symbol state to free lines and avoid leaks across many PR events in a session.

## Caveats
- **250 ms data is genuinely stale for a fast mover.** You are always reacting to an ask that may already be gone; the offset compensates but cannot eliminate slippage. If sub-250 ms reaction is truly required, the only IBKR answer is tick-by-tick or native pegs — and tick-by-tick conflicts with the user's line-budget constraint, which is exactly why native pegs deserve strong consideration.
- **`placeOrder` has no synchronous confirmation and IBKR's API→market latency is unbounded in practice** — community reports describe modifications/cancels taking "anywhere from 1 to 10 seconds" to reach the market in volatile conditions, during which the *old* price/size is still fully live and fillable. Your code must never assume a modify took effect until a callback confirms it; design for "the order may fill at the old price at any moment."
- **Race condition: a modify can arrive after a fill.** If the ask jumps and you send a re-price while the order is filling, you may get error 10147/10148 ("cannot be cancelled/modified, state: Filled") or a modify against an already-complete order. Treat these as benign and resync from `orderStatus`; do not blindly retry.
- **Failed modifications can desync client libraries.** A rejected modify (e.g., bad price increment) can produce a `Submitted → Modified → Cancelled` sequence where only the *modification* was rejected but the original order is still live; some wrapper libraries (ib_insync) have historically dropped the order from their open-orders view in this case. Reconcile against `reqOpenOrders`/`reqAllOpenOrders` after any unexpected `Cancelled`.
- **OER enforcement is opaque and somewhat discretionary.** IBKR measures it daily but warns/acts over multi-day windows; low absolute order counts (a couple hundred/day) rarely trigger action regardless of ratio, but thousands of place/edit/cancels with few fills will. Don't assume you're safe just because you're under 50.
- **The "modify resets filled to 0" claim is wrong** for same-orderId modifies but is a real point of confusion online; the safe, verified practice is to keep `totalQuantity` at the original size. The one item not authoritatively pinned down is the exact error code when a modify's `totalQuantity ≤ filled` — confirm empirically in paper.
- **Queue-priority and ETH-liquidity effects mean this technique is a slippage-management tool, not a price-guarantee.** Orders guarantee a fill or a price, never both; in a thin ETH book during a PR spike, even a well-tuned chase can fill poorly or not at all up to your cap.
