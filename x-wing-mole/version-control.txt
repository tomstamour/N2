x-wing-mole — version control
================================================================================
IBKR (ibapi) trading trio. A trade-frequency surge detector (trade-mole) hands a
buy-signal to a yield-laddered trailing-stop trader (x-wing); a clerk runs BOTH
as an in-process "duo" on ONE shared, pre-warmed ibapi client from a pool.

Live chain (three separate processes):
    RTPR_connector3 ─tcp8900─► orchestrator5 ─tcp8765─► clerk-1.1 ─► Gateway
Current live scripts: clerk-1.1.py, trade-mole-2.1.py, x-wing-2.1.py.
Run everything with the venv python (system python3 lacks ibapi).
Ports: 4001 = LIVE Gateway, 4002 = paper GW, 7497 = paper TWS.

Legacy X-wing-1.0.py and trade_mole_4.1.py have been DELETED (refactor complete);
only their successors remain on disk.


================================================================================
x-wing  —  yield-laddered trailing-stop trader (long side, one symbol)
================================================================================
Constant across versions:
  - On buy-signal: BUY LMT for floor(CAPITAL / entry) shares, then a protective
    SELL STP LMT that RATCHETS (only ever moves UP, holds when price falls). A
    synthetic trigger converts it to a SELL LMT at the held table limit to force
    the ETH-safe exit. Yield -> Trigger%/Limit% comes from the banded limits TSV.
  - Never uses reqGlobalCancel (would nuke other instances on the shared account)
    or reqTickByTickData (3-request cap).

1.0  ->  2.0     (X-wing-1.0.py -> x-wing-2.0.py; 1.0 no longer on disk)
--------------------------------------------------------------------------------
  - REMOVED (per the 2.0 docstring): the re-entry loop, the --exit-cross-percent
    second-buy logic, and the 1.0 SIGUSR1/--prewarm arming path. No re-entry now:
    when the protective sell fully fills, the run is done.
  - Two run modes: STANDALONE (its own single ibapi client for data+orders;
    SIGUSR1 = manual fire) or DRIVEN (the clerk injects ONE shared client and fans
    ticks into update_quote(); trade-mole calls on_buy_signal() — x-wing opens no
    socket of its own).
  - Behaviours in the 2.0 line (all inherited unchanged by 2.1):
      * Entry reference = the HIGHER of (ask, trigger-print, last); the 4% entry
        pad widens to 6% when the ask is detectably stale vs the trigger print
        (added 2026-07-22, after the DAIC stale-ask miss).
      * Entry-fill timeout lowered 30s -> 10s (2026-07-22); on timeout the resting
        BUY is CANCELLED, never left working.
      * Realizable exit reference is the BID (a wide/phantom ask cannot inflate the
        yield or the protective stop).

2.0  ->  2.1     (x-wing-2.1.py)                                        [CURRENT]
--------------------------------------------------------------------------------
  - ADDED the IBKR Price Management Algo on the BUY ENTRY ONLY:
    Order.usePriceMgmtAlgo = True, gated by the module constant
    ENTRY_USE_PRICE_MGMT_ALGO (set it False to fall straight back to 2.0
    behaviour). Implemented as an opt-in `use_price_mgmt_algo` argument on
    limit_order(); place_entry() is the ONLY caller that passes True.
      WHY: the marketable pre-market BUY LMT (ref*1.04, or *1.06 on a stale ask)
      can be more aggressive than IBKR's pre-trade price-cap check and get
      rejected — either as a silent "Inactive" with no error reason
      (rejected-orders-findings.txt: CLIK, OFAL) or as error 202 "limit price too
      aggressive". PMA makes IBKR CAP the price to the allowed band and WORK the
      order instead of rejecting it.
  - UNCHANGED: the entry-pricing math (4% / 6% stale / 30% cap), the ratchet
    ladder, every timeout, the reject/dead-status handling, and the public API the
    clerk imports (build_driven, run_trade, on_buy_signal(last_ask, trigger_print),
    setup_logging, LOG_DIR, parse_hhmm, make_contract, route_tick_price).
  - The protective SELL STP LMT and the exit/flatten SELL LMTs DELIBERATELY do NOT
    set the flag (PMA on stop orders is undocumented/unverified).
  - Note: usePriceMgmtAlgo is a standalone Order boolean, NOT an algoStrategy —
    no algoParams/TagValue. Present in ibapi 9.81 and wire-gated by
    MIN_SERVER_VER_PRICE_MGMT_ALGO = 151 (modern Gateway is far past that).
  - STATUS: local verification passes (the placed entry carries the flag; stop /
    exit orders do not; pricing constants intact). Live effectiveness against the
    pre-market reject is still to be confirmed on the paper GW (4002).

clerk  —  warm ibapi client pool + orch-trigger listener (runs the duos)
================================================================================
Current: clerk-1.1.py (clerk-1.0.py superseded; not on disk).
  - Holds a pool of pre-connected clients (ids 1000..1029). On an orch-trigger
    {ticker, lastDailyClose, itiBaseline, tradeSizeBaseline} it picks a FREE warm
    client and runs a trade-mole + x-wing duo on that ONE shared socket, then
    RESETS it (cancelMktData + clear state) and returns it to the pool WITHOUT
    dropping the socket.
  - Reads clerk-trigger-conditions.txt ONCE at startup: per-ET-window mole lifeTime
    + finbert_gate on/off (missing/malformed -> built-ins 02:30 / gate on).
  - Deferred (closed-market) duos are persisted to clerk_state/pending_duos.json
    and replayed / re-armed on restart; a reconnection watchdog re-warms the pool
    after the daily Gateway restart.
  - Loads its duo scripts BY FILENAME via _load_module (clerk-1.1.py): currently
    "trade-mole-2.2.py" (since 2026-07-30; clerk-1.2 switched too) and
    "x-wing-2.1.py" — this loader line is the single edit needed to point the
    live chain at a new x-wing / trade-mole version.
  A precise 1.0 -> 1.1 changelog is not recorded in-repo (1.0 is gone); the entry
  above describes the current 1.1 architecture.

2026-07-28  BUGFIX (clerk-1.1.py AND clerk-1.2.py) — deferred sessions were
            killed by a sentiment gate that did not apply to them
--------------------------------------------------------------------------------
  Symptom: BKYI (PR 02:59 ET, deferred to a 04:00 collection start) surged at
  04:00:02 and trade-mole recorded ZERO data points / wrote no output file.

  Cause: the "Sentiment BAD" handler resolved the trigger regime with
  conditions.at(datetime.now()) — i.e. the instant the BAD ARRIVED (02:59 ->
  DEFAULT -> finbert_gate=on -> tear down). But the session was deferred to
  collect at 04:00, which resolves to WINDOW 04:00-06:59 -> finbert_gate=off,
  where sentiment has NO authority and the surge is the sole trigger. finish()
  then cancelled the pending defer timer, so reqMktData was never issued and the
  session was gone 61 min before the surge.

  This contradicted the design already stated elsewhere in the file:
  on_buy_signal resolves finbert_gate at the SURGE instant, and
  _begin_collection anchors the watch lifetime on COLLECTION START, explicitly
  noting "04:00 ET for deferred overnight duos, not trigger arrival". The BAD
  handler was the one place that missed the same consideration. For a live-market
  session arrival ~= surge, so it never showed there.

  Hit rate on the affected path was 100%: of 5 deferred sessions in 8 days of
  clerk logs, 4 died this way (PMI 07-21, CRMT 07-21, MSGM 07-22 on clerk-1.1;
  BKYI 07-28 on clerk-1.2). EDHL 07-26 had no BAD, survived, and collected
  normally at 04:00 — the control case.

  Fix: new DuoSession/TrioSession.conditions_instant() returns the scheduled
  collection start while the session is still deferred (_defer_target set and
  _watch_timer not yet armed) and `now` once collection has begun; the BAD
  handler resolves against it. The existing gate-off branch already did the right
  thing — it was simply never reached. _defer_target is left untouched so the
  crash-replay record and arm reply are unaffected.

  BEHAVIOUR CHANGE (intended): an overnight BAD-sentiment PR now survives to
  04:00 and may trade on surge alone, which is what finbert_gate=off means for
  that window. Intraday behaviour is unchanged (BAD still tears the session down).

  Also: Orchestrator5.2 now logs the three gate inputs against their thresholds
  on the BAD path ("[Gate] SYM BAD: positive=... indecisive=... combo=..."), so a
  rejection is diagnosable from the log without joining it to the TSV by hand.

2026-08-02  T47-airspeeder-1.0.py  ->  T47-airspeeder-2.0.py  (clerk-1.2 switched)
            the 4-run DROP/PUSH ladder becomes ONE re-entry at SP1
--------------------------------------------------------------------------------
  Both versions are on disk; clerk-1.2.py's _load_module line is the only wiring
  (t47mod = _load_module("t47_airspeeder", "T47-airspeeder-2.0.py")). The
  clerk-facing API is byte-identical — set_anchor / launch_run1 / on_tick_price /
  observe_order_status / on_run_done / shutdown — so nothing else changed, and
  x-wing-2.1.py / trade-mole-2.2.py / clerk-1.1.py were not touched.

  WHY: 1.0's re-entry rule carried a lot of state (HP re-anchoring on every new
  high, HP_RESET, a PUSH threshold off LP, an LP dwell timer, up to 3 relaunches)
  for a behaviour that had never been validated live. 2.0 keeps the entire safety
  layer and replaces only the watch arithmetic with the rule drawn on slide 2 of
  the design deck: PR -> EP1 -> HP1 -> SP1 -> EP2.

  THE RULE (2.0): at the run-1 exit the exit avg fill is FROZEN as `level` (SP1)
  and never re-anchors. While flat, LP tracks the lowest bid since that freeze;
  DIP = (level - LP)/level*100 >= EP2_MIN_DIP_PCT (10.0) latches Valid-DIP; the
  first bid >= level after that relaunches ONE fresh x-wing, priced the same way
  1.0 did (on_buy_signal(ask, ask), Rule-F shape, session.xwing swapped BEFORE
  the place). XWING_REENTRY_NUMBER = 1 => 2 runs max. Setting EP2_MIN_DIP_PCT = 0
  disables the dip gate (any re-cross fires); both comparisons are >=.

  ABORTED RUN 1 (entry Inactive / timeout / reject, so no SP1 exists): still gets
  its one re-entry, aiming at ctl.trigger_print -> ctl.ask -> current bid. 1.0
  re-anchored to the bare bid instead.

  DROPPED constants: DROP_THRESHOLD_PCT, PUSH_THRESHOLD_PCT, LP_DWELL_SEC.
  UNCHANGED: T47_WATCH_LIFETIME (2h from collection start) + T47_SESSION_END_ET
  (20:00), both flat-only; the heartbeat that only sets _pending_finish while a
  run is live (T47 still never touches ctl.stop_evt); the _prior_entry_ids
  late-fill guard; t47:residual_position / t47:late_entry_fill /
  t47:budget_exhausted:* / t47:launch_failed / t47:lifetime / t47:session_end.

  OUTPUT: T47-tables/SYMBOL-yyyy-mm-dd-hh-t47v2.tsv — new "v2" suffix because the
  ten 1.0 tables from 2026-07-28 in that directory carry the old column set. 13
  columns: Time, CP-Bid, Ask, EP, SP, HP, LP, DIP(%), GAP(%), Valid-DIP, Run,
  State, Event. SP shows the FROZEN level while the watch is open (so "the bid
  came back to SP" reads off one row) and the latest exit fill otherwise;
  GAP(%) = (bid - SP)/SP*100, i.e. 0.00 is the fire line; HP mirrors x-wing's
  in-position high_water and is INFORMATIONAL ONLY (it drives nothing in 2.0).
  Events: RUN_LAUNCH / ENTRY_FILL / EXIT_FILL / LATE_FILL / ABORT / LEVEL_SET /
  VALID_DIP / RELAUNCH / LIFETIME_END / SESSION_END / CLIENT_DEAD / DONE:{reason}
  (1.0's HP_RESET is gone — the level never re-anchors).

  ALSO FIXED (carried over from 1.0): T47Writer.close() closed the handle but
  left _fh non-None, so `opened` stayed True and a post-shutdown write would hit
  a closed file. 2.0 nulls _fh, sets a _closed flag that makes write() a no-op,
  and tracks "a file was ever created" in a separate _ever_opened flag (that is
  what keeps a no-surge session from leaving an empty TSV).

  VERIFIED: offline stub harness (T47 is ibapi-free and takes an injectable
  clock) — 9 cases all pass: 5% dip then re-cross does NOT fire; 11% dip then
  re-cross fires exactly once with session.xwing swapped BEFORE on_buy_signal;
  run 2 end -> budget_exhausted, never a 3rd run; aborted run 1 aims at the
  trigger print; late fill on the dead entry ends the trio; residual position
  ends the trio; flat lifetime expiry -> t47:lifetime; no-surge session leaves no
  file; TSV shape + post-close write dropped. PAPER-GW VERIFY STILL PENDING (as
  it was for 1.0 / clerk-1.2 as a whole).

Operating rules (cross-cutting)
================================================================================
  - Run exactly ONE connector variant + ONE orchestrator + the clerk; never two
    orchestrators (double-arm).
  - clientIds are a limited Gateway resource: clerk pre-claims 1000–1029,
    dailyStats 77, daily-board 20000. Saturation shows up as handshake timeouts.
  - Bulk historical-data jobs go on the idle paper GW (4002); the live GW (4001)
    drops them under contention.
