Orchestrator5 — version control
================================================================================
One standalone process that turns the RTPR firehose news stream into (a) a daily
TSV of scored press releases and (b) real-time arm/sentiment trade signals to the
clerk's warm IBKR client pool.

Constant across 5.0 / 5.1 / 5.2 / 5.3 / 5.4 (architecture unchanged):
  - Standalone feed-client of RTPR_connector3 over loopback TCP 127.0.0.1:8900
    (successor of orchestrator3/Orchestrator4.2.py).
  - Reception in _on_row_built (main/feed thread, kept lean) -> per-ticker
    _collect_and_log on worker pools.
  - Per-day article-ID dedup + same-day (headline+tickers) content dedup
    (RTPR re-publishes under new IDs: PRZO, FOFO).
  - Two kept NW4 input filters (ticker count <= 2; NW4 excluded_strings drop) +
    local arm-block excluded_strings-2.txt.
  - Clerk handshake: STEP 1a ARM on reception, STEP 1b SENTIMENT "OK"/"BAD" after
    scoring. Missed-while-disconnected PRs are dropped by design (gap logged).
  - Run exactly ONE orchestrator at a time — never two of 5.0/5.1/5.2/5.3/5.4
    (double-arm).

!! FROM 2026-08-17 THE GATE IS NOT A FLAT OR.  A `REQUIRE <Name>: ...` line is a
   PRECONDITION, AND-ed over the whole gate, so
       gate = (every REQUIRE line holds) AND (any ordinary rule fires)
   One ships (ClassWhitelist).  Two consequences for anyone reading old tooling:
   a Trigger cell verdict of `NO` no longer implies every group reads `:NO`, and a
   REQUIRE condition FAILS CLOSED — a dead scorer behind one stops ALL trading.

5.2 in-place change #3  (2026-07-29)  — `Trigger` COLUMN
   [superseded by change #4 (2026-08-01), which kept the cell but made the gate an AND]
--------------------------------------------------------------------------------
Observability only — the GATE IS UNCHANGED (same three legs, same five thresholds,
same fire/no-fire decision on every row).  ClerkSentiment is byte-identical to
change #2: verified over all 243 combinations of pass/fail/None for the five gate
inputs (all 8 labels exercised) that the new code returns the same (is_ok, label)
as the pre-change body.
TSV: 38 -> 39 columns.
  - Added `Trigger` as the LAST column, so every pre-existing column keeps its
    index and positional readers of the new files still work.
  - Grammar (one tab-free, newline-free cell):
      <YES|NO> | FinBERT:<v> FMB:<v> kw15_body:<v> kw15_head:<v> FLANG:<v>
    All five tokens always present, always in that order.  <v> is one of:
      PASS(<score><op><thr>)  condition held
      FAIL(<score><op><thr>)  condition failed
      MISSING                 score was None (model error / future timeout)
    <op> is always the relation that is TRUE of the row: >= / <= on a pass, its
    negation < / > on a fail.  FMB is the ONLY <= condition (indecisive is a
    ceiling, the other four are floors).  Scores print at 4 dp (display only — the
    PASS/FAIL token is authoritative); thresholds at 2 dp when that round-trips
    exactly, else %g, so a retuned 0.625 never prints as a misleading 0.62.
  - Example:
      YES | FinBERT:PASS(0.8231>=0.60) FMB:PASS(0.0512<=0.13)
            kw15_body:FAIL(0.3104<0.60) kw15_head:FAIL(0.4412<0.65)
            FLANG:FAIL(0.6210<0.97)                      [one cell, wrapped here]
Why, given ClerkSentiment already names the fired legs:
  - A leg is an AND of two models, so `BAD` never said WHICH half failed.  The
    motivating case is FinBERT 0.74 PASS + FMB 0.31 FAIL -> no fire, which was
    previously indistinguishable in the TSV from a row where everything scored ~0.
  - Near-misses become greppable, which is what retuning a threshold needs.
  - A dead scorer (None) is now MISSING rather than silently reading as a low
    score.  That distinction previously existed only in logs/.
  - Trigger is written on EVERY row — the gate runs before the arm branch — so it
    survives the skipped:excluded_string / skipped:arm_rejected / skipped:not_armed
    rows where ClerkSentiment discards the verdict entirely.
Implementation:
  - _evaluate_trigger now returns (is_ok, label, detail) — one call site.
  - The five per-condition verdicts are named locals (c_fin/c_fmb/c_body/c_head/
    c_fla) feeding BOTH the legs and the cell; _cond_token takes the verdict as a
    PARAMETER rather than recomputing the comparison, so the cell cannot disagree
    with the gate that fired.
  - The [Gate] BAD log line (which used to hand-list the same 5 inputs vs the same
    5 thresholds in a 9-arg format string) now logs `detail` verbatim — one source
    of truth, and log == TSV cell by construction.
  - Console block prints both `Trigger` (the cell) and `Trigger legs` (the label).
⚠ Rotation: the live process at the time of this edit was still the pre-FLANG
  31-col build, so the first restart rotates today's 31-col file to
  news_output_<date>_rotated.tsv and starts a fresh 39-col file.  os.rename
  CLOBBERS an existing _rotated.tsv for the same day — back the file up before a
  second same-day schema switch, and note daily-board.py tails the live path and
  will silently follow the new empty file.

5.2 in-place change #4  (2026-08-01)  — GATE: OR -> AND + ALL FIVE THRESHOLDS
                                        RETUNED
   [still a complete branch, but see 08-02 and 08-03 below: it is now one of FOUR,
    and the 08-03 solo legs subsume it above kw15_body 0.70 / FLANG 0.975]
--------------------------------------------------------------------------------
This is a TRADE-BEHAVIOUR change, not observability.  The gate stops being an OR
of three legs (ANY one fires) and becomes an AND of all five conditions (EVERY
one must hold), and every threshold moves at the same time.

                        old            new
  SENTIMENT_POSITIVE_MIN 0.6      ->    0.8     FinBERT positive        (floor)
  FMB_INDECISIVE_MAX     0.13     ->    0.14    FinMarBa indecisive     (ceiling)
  KW15_BODY_MIN          0.60     ->    0.50    ge15 body model_proba   (floor)
  KW15_HEAD_MIN          0.65     ->    0.50    ge15 head model_proba   (floor)
  FLANG_SCORE_MIN        0.97     ->    0.96    FLANG sentiment_score   (floor)

The three LEGS survive as names only.  Each leg is itself an AND, so "all three
legs" and "all five conditions" are the SAME boolean function — the legs are now
a grouping, not alternatives, and the FLANG leg is NO LONGER STANDALONE.

Calibration (2026-08-01), on price_stats_loader/outputs/
  06_PRstats_2026-06-22-2026-07-30_11EncBodyHeadScored_kwScored_FinBERT.tsv
(1055 labelled rows; the full-coverage FinBERT_positive / FinMarBa_indecisive
columns — note FMB_indecisive is populated on only 143 rows in that file and
using it instead understates the AND badly):
                                       fires         P@>=30%  lift    recall
  OLD  OR  0.6/0.13/0.60/0.65/0.97      267 (25.3%)   32.6%   1.90x   48.1%
  NEW  AND 0.8/0.14/0.50/0.50/0.96       26 ( 2.5%)   46.2%   2.69x    6.6%
At the >=15% target the AND gate runs 80.8% precision / 2.51x lift (base 32.2%).
The retuned cuts are matched TO the AND: loosening kw15 to 0.50/0.50 and FLANG to
0.96 more than DOUBLES the fire count vs AND-with-the-old-thresholds (11 -> 26) at
essentially unchanged precision, while FinBERT tightens 0.6 -> 0.8.  Deliberate
trade: ~1 trade/day at a much higher hit rate, accepting the recall collapse.
⚠ n=26 — 46.2% carries roughly a +/-19pp CI and is post-selection (the thresholds
  were chosen against this same file).  An operating point, not a measurement.

TSV: 39 columns, UNCHANGED.  No header change means NO rotation and no
  _rotated.tsv — and also that the header does NOT tell you which gate wrote a
  row.  Use the date, or read the per-row Trigger cell: it embeds the thresholds
  in force, so rows written either side of the restart are self-describing even
  within one daily file.
ClerkSentiment: DEGENERATE from this date.  The label is still BUILT by joining
  fired leg names in the fixed order Keyword, FinBERT_FMB, FLANG, but is now gated
  on is_ok rather than on a non-empty `fired` list.  Since is_ok implies all three
  legs, only two values can occur: "Keyword_FinBERT_FMB_FLANG" and "BAD" (plus the
  unchanged skipped:*).  The other six OR-era labels (FLANG, Keyword_FLANG,
  FinBERT_FMB, Keyword_FinBERT_FMB, FinBERT_FMB_FLANG, Keyword) are UNREACHABLE.
  Old parsers keep working — they just see one label.  Trigger is now the only
  informative gate cell.
Implementation:
  - is_ok = c_fin and c_fmb and c_body and c_head and c_fla  (was bool(fired)).
  - label = '_'.join(fired) if is_ok else 'BAD'  (was `if fired else 'BAD'`).
    THIS GUARD IS LOAD-BEARING: under AND a row can have one leg true and still not
    fire, and the old expression would have labelled such a row "FLANG" while the
    gate said BAD — the TSV would have contradicted the trade.
  - _evaluate_trigger now returns a 4th value, missing_blocked: True when >=1 score
    is None AND every condition that COULD be evaluated passed.  Rationale: a None
    still kills only its own condition, but under AND that single false blocks
    EVERY trade, where under OR another leg could still fire.  A silently dead
    model is therefore indistinguishable from a quiet news day by fire count, so
    _collect_and_log escalates that case to logger.warning("... BLOCKED BY MISSING
    SCORE ONLY ...").  Grep it when the tape looks suspiciously silent.
  - One call site, unpacked to 4 values.  Trigger cell format is UNCHANGED.
Verified:
  - Exhaustive 3^5 = 243 pass/fail/None check against the live _evaluate_trigger
    (same method as change #3): is_ok == AND of the five conditions on every case;
    label == 'BAD' on every non-firing case; missing_blocked true on exactly the
    31 (= 2^5 - 1) cases with >=1 None and all evaluable conditions passing;
    Trigger always 5 tokens, MISSING iff the score was None.  Exactly 1 of 243
    cases fires.  Labels observed: {BAD, Keyword_FinBERT_FMB_FLANG} only.
  - Corpus replay through the LIVE function reproduces the table above exactly
    (26 fires, 80.8% @>=15%, 46.2% @>=30%).
  - Replay over the 137 live 39-col rows in tables/: the AND gate fires 4 where the
    OR build fired 27, and never fires on a row the OR gate rejected (subset).

2026-08-02 — EARNINGS TRADE LEG: PrClassifier + earning_scorer, OR-ed with the AND
================================================================================
WHAT: a SECOND trade branch beside the 2026-08-01 five-way AND.  The AND itself is
  untouched and still a complete branch; a row can now ALSO fire on

      FineClass == 'Earnings_Results' AND EarningScore >= 4 AND kw15_body >= 0.50

      is_ok = core_and OR earnings_leg

  kw15_body is the SAME c_body local the core branch uses — one condition, two
  branches.  FinBERT / FMB / FLANG / kw15_head are NOT consulted by this leg.

WHY: the core AND is structurally BLIND to earnings PRs.
  tools/Earning_Scorer/Earnings_text_structures_report.md §4 measured the gate's own
  FinBERT headline score at test AUC 0.297 on earnings PRs — ANTI-predictive.  Cause:
  winners and duds share near-identical headlines ("X Reports Q1 2026 Financial
  Results"); the separating numbers are in the BODY.  So the five-way AND cannot
  select within this class at all, no matter how it is retuned.

CALIBRATION (2026-08-02, on
  tools/Earning_Scorer/PRstats_2026-05-04-2026-07-30_EarningResults_earnScored.tsv —
  518 labelled Earnings_Results rows, base rate 7.1% on fromPR_High >= 30%, with
  kw15_body recomputed by the frozen ge15 body pipeline):

      gate                                  fires   prec@>=30%   lift
      current five-way AND on these rows        3       0.000       —
      EarningScore>=4 AND kw15_body>=0.50      36       0.472      6.6x
      test block only (>=2026-06-20, n=79,      7       0.429      3.1x
        base 13.9%)

  OVERLAP WITH THE AND BRANCH IS EXACTLY ZERO — purely additive, ~0.71 extra
  trades/day at the same precision bar the AND branch holds (46.2%).
  Cut choice: precision is FLAT below 4 (>=1 .321, >=2 .314, >=3 .339) and steps up
  at 4 (.472).  4 is the knee and matches the report's own defensible operating point.
  Neither leg alone is enough: EarningScore>=4 alone .253, kw15_body>=0.50 alone .234
  — the AND is what buys the lift.
  !! n=36 => wide error bars, and EarningScore is a RANKING CUT, not a calibrated
  probability: the >=30% base rate itself moved 3.7% (May) -> ~15-20% (Jun/Jul).

!! EarningScore is INTEGER POINTS (observed -7..+9, median 0), NOT a 0-1 score.
  A threshold like 0.4 would silently mean ">= 1" — 36.5% of earnings PRs at 32%
  precision.  The points come from tools/Earning_Scorer/earn_score_params.json
  (calibrated 2026-08-01, FROZEN): changing that file changes what ">= 4" means.

Implementation:
  - Two new path-loaded modules (neither has a hyphen, but neither dir is a package
    and `earning_scorer` is a generic name):
      tools/categorizer/PrClassifier.py     -> classify_pr, PRCLASS_BODY_LEAD_CHARS
      tools/Earning_Scorer/earning_scorer.py-> earn_extract_metrics,
                                               earn_score_metrics, earn_load_params
    Both import-safe + thread-safe; no sys.modules pre-registration needed.

2026-08-17 — CLASS WHITELIST: a REQUIRE precondition gates every rule  [CURRENT]
================================================================================
WHAT: a new RULE KIND in orchestrator_trigger_rules.txt.  A line prefixed
  `REQUIRE ` is a PRECONDITION: it never fires anything, it only permits, and
  every one of them is AND-ed over the whole gate.  So the gate is no longer a
  flat OR:

      gate = (every REQUIRE line holds) AND (any ordinary rule fires)

  One REQUIRE line ships, first in ACTIVE RULES:

      REQUIRE ClassWhitelist: FineClass in MA, Partnership, Regain_Compliance,
              Clinical_Data, Contract_Award, Patent_IP, Earnings_Results

  (one physical line in the file).  CORE / EARNINGS / KwBodySolo / FLANGSolo /
  FinBERTSolo are UNCHANGED, character for character — they are simply now
  conditional on the catalyst class.

  Second new feature, needed to express it: the `in` / `not in` OPERATOR on
  string fields, taking a comma-separated list (braces optional on input, always
  printed on output).  The DSL has no OR inside a line, so without `in` a
  7-class whitelist would have been 7 rules per branch = 35 lines.

WHY: every cut in the gate reads a SENTIMENT score; none reads the catalyst
  TYPE.  A confidently-positive headline therefore fires whether the PR is an
  acquisition or a share offering, and the false positives concentrate in the
  classes that barely move.  From
  ../price_stats_loader/outputs/08_class_trading_value.md, honest window:
  `Other` 18.8% / `Product_Launch` 8.3% / `Offering_Financing` 10.0% /
  `Clinical_Update` 0% against `Partnership` 46.2% and `MA` 32.1%.

  ⚠ A class VETO was measured first and rejected: dropping the six worst classes
  moves precision 22.0% -> 22.6%, because the sentiment cuts already almost never
  fire there (8 fires total across all six).  Only a WHITELIST moves the number,
  and that is what this is.

BEHAVIOUR CHANGES (three, all in the Trigger cell; the wire is untouched):
  1. A REQUIRE group prints ALLOW / BLOCK, not YES / NO.  `grep -c ':BLOCK\['

COMPANION BUG FIX, required by the above: _classify_and_score_earnings returned

  already succeeded.  Its own docstring promised "a dead earnings scorer costs

Implementation (Orchestrator5.2.py):
  - _op_in / _op_not_in: thin wrappers, because operator.contains(a,b) is `b in
    a` — reversed from every other _OPS entry.  Wrapping keeps _cond_true a
    single uniform cond.fn(lhs, cond.rhs) call with NO per-operator branch on the
    trade-critical path, so `in` costs nothing there.  Still no eval(): the
    operator is looked up in a closed whitelist keyed by literal text and bound
    once at parse time; that guarantee never rested on the callables being
    `operator` builtins.
  - _OP_CELL, a THIRD table beside _OPS/_OP_NEG: `in`/`not in` are WORDS and a

  - _Rule gains `kind`, LAST and defaulted, so 4-positional construction still

  - _REQUIRE_PREFIX_RE is `^REQUIRE(?:\s+|$)`, stripped BEFORE the ':' partition

  - _log_active_gate prints REQUIRE lines first and marks them in the per-source

    so the verdict is frequently forced before the leg exists:
      - a REQUIRE already failed              -> BAD, whatever the score
      - no FIRE rule can still hold           -> BAD, whatever the score
      - every REQUIRE holds AND one rule fires-> OK,  whatever the score
      - otherwise                             -> None, and only then do we wait
    Measured on 890 tape rows: 65.7% forced BAD, 3.7% forced OK, 30.6% wait.
    A condition is PENDING exactly when its field's source is in _XGB_GATE_SOURCES.

    SAFETY NET, and it is not optional: after the leg lands, _collect_and_log
    re-runs the REAL _evaluate_trigger over the complete inputs, writes THAT into
    Trigger / ClerkSentiment / the dead-scorer alarm, and logs at ERROR if the early
    answer disagreed with it. So the TSV is byte-for-byte what it would have been,
    and a logic bug would be loud rather than silent.
