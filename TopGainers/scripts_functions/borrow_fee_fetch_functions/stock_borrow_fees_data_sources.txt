II. Foundational Understanding of IBKR Securities Lending Data

Programmatic access to short selling data requires an understanding of how IBKR calculates, updates, and distributes the underlying figures, particularly differentiating between the rate used for client monitoring and the final rate applied for billing.

A. The Nature of the Borrow Fee Data

1. Indicative Rate vs. Final Cost Calculation

The data retrieved through programmatic interfaces, whether API or FTP, provides the indicative borrow rate used for ongoing monitoring and projected cost analysis. This rate is an estimate of the current market rate for borrowing that specific security.  

The final borrow fee assessed to the client account is a highly complex calculation performed daily and displayed on the monthly Activity Statement. This final fee is calculated using the following structure :  

Borrow Fee=(Value×Fee Rate)/360

Crucially, the "Value" in this formula is not simply the market price multiplied by the quantity. Instead, the collateral value used to determine the hard-to-borrow fees is based on an adjusted price. Industry convention generally requires a deposit equal to 102% of the prior day's settlement price, which is then rounded up to the nearest whole dollar and multiplied by the number of shares borrowed. The Fee Rate (%) applied is determined after IBKR applies its own 102% markup and rounding conventions. Therefore, the indicative rate retrieved programmatically is a critical input, but the final cost calculation is multi-layered, particularly affecting low-priced or hard-to-borrow securities.  

2. Data Update Frequency and Prerequisites

While IBKR’s core market data stream (e.g., price, size) is designed for extreme low-latency environments, updating four times per second (every 250 milliseconds) via socket connection , the indicative borrow rate is a slower-moving, strategic data point. The system documentation confirms that the indicative borrow rate is updated only periodically throughout the day. This lower update frequency reinforces the operational validity of using a daily, stable bulk download (like the FTP method) for strategic rate analysis, rather than relying on complex, persistent, low-latency API infrastructure solely for a value that does not update on a tick-by-tick basis.  

Furthermore, utilization of the TWS API or the Client Portal API for market data retrieval carries specific prerequisites. API functionality is considered "off-platform" by exchanges, meaning users typically require paid market data subscriptions. Access also requires an active, funded IBKR account, generally with a minimum balance of $500 USD. The Client Portal Web API is specifically restricted to IBKR PRO account types.  

B. Mandatory Filtering: DTC Continuous Net Settlement (CNS)

A secondary layer of data validation is imposed by IBKR's short-selling policies, which must be incorporated into any robust quantitative system utilizing this data.

1. DTC CNS Constraint

IBKR maintains a strict criterion regarding the types of US stocks eligible for short sale orders. The firm does not accept short sale orders for US stocks that are not eligible for DTC continuous net settlement (CNS). This constraint dictates the ultimate tradability of any security identified as "shortable."  

2. Pre-Processing Requirement Implication

The consequence of the DTC CNS constraint is that simply retrieving the list of "shortable securities grouped by country" from IBKR is necessary but not sufficient for determining trade eligibility.  

If the retrieved daily file contains securities that IBKR lists as shortable but are ineligible due to the CNS requirement, a trading algorithm that relies solely on the IBKR-provided file could attempt to short a prohibited security. Therefore, a quantitative system must incorporate an internal filtering layer post-download. This layer involves cross-referencing the retrieved indicative borrow rate data against independent or derived CNS eligibility data for US stocks. This additional data processing step ensures that the short sale orders conform to IBKR’s internal compliance rules, preventing order rejection and ensuring system integrity.

III. Method 1: Bulk Data Retrieval via Public FTP (The Recommended Solution for Rate %)

For algorithmic systems requiring a comprehensive, daily list of indicative borrow rates for strategic cost modeling, the Public FTP site is the most effective and simplest command-line accessible solution. This method requires no complex API libraries or persistent socket connections, relying instead on universally available network utilities.

A. Architecture and Access Protocol

Interactive Brokers maintains an explicitly supported Public FTP endpoint designed for data delivery, particularly for short stock availability.  

    Connection Details: Access is standardized and anonymous. The required host address is ftp2.interactivebrokers.com.   

Credentials: The designated username for access is shortstock, and importantly, the password field must be left empty.  

Command-Line Integration: This protocol facilitates straightforward scripting using standard command-line tools available across major operating systems (Windows Command Prompt, macOS, Linux Terminal). The standard workflow involves initiating the connection, authenticating with the fixed credentials, listing the contents of the directory (dir or ls), and then issuing a get filename.txt command to download the desired US short stock file. The anonymity and fixed credentials make this connection highly predictable and simple to wrap in shell scripts or batch files for unattended daily automation.  

B. File Structure and Content

The purpose of the FTP site is to allow clients to "Download prepared lists of shortable securities grouped by country".  

    File Naming and Format: While the exact daily filename for US data is dynamic or not explicitly listed, the files are typically structured text or CSV formats, derived from data sets that list securities by country (e.g., US stocks are grouped by USD currency). The content includes fundamental identifier fields such as Symbol, Currency (USD), and Long Name.   

Rate Inclusion: Based on the service description (which promises "prepared lists of shortable securities" ) and the need for comprehensive cost data, this bulk file is the expected repository for the daily indicative borrow rate percentage for all listed instruments. The file provides the necessary breadth for market scanning that the real-time APIs cannot efficiently deliver.  

C. Operational Reliability Through Public Utility

The reliance on a Public FTP utility for strategic data collection offers significant operational advantages over the real-time API methods, particularly for quantitative systems prioritizing stability and minimal operational overhead.

The FTP method requires no proprietary API wrappers (like ibapi), no persistent socket connection (unlike TWS API), and no running authentication daemon (unlike CP Gateway). It functions independently of the client's account funding status, API subscriptions, or the need to maintain a local running instance of TWS or IB Gateway. Furthermore, standard FTP bulk data transfers are typically exempt from the severe, per-request pacing limitations imposed on API endpoints. This low barrier to entry and robust simplicity makes the Public FTP the superior choice for retrieving the complete, daily snapshot of the indicative borrow rate percentage for all US shortable equities.  

IV. Method 2: Real-Time Access via TWS API (ibapi)

The Trader Workstation (TWS) API, accessed via the Python wrapper (ibapi) or other language implementations, is the established method for highly granular, tactical execution data. However, its complex architecture and specific data limitations render it unsuitable for simple bulk rate retrieval, mandating its use be focused narrowly on real-time share availability.

A. TWS API Infrastructure and Operational Requirements

    Architecture and Dependencies: The TWS API operates fundamentally as a TCP Socket Protocol and relies on a message-based structure. It is not a standalone web service; it requires continuous connectivity to a locally running instance of either the Trader Workstation (TWS) or the unattended IB Gateway. This requires maintaining a dedicated daemon process on the user's local or virtual machine. Implementation requires expertise in Object-Oriented Programming (OOP) concepts to properly handle the asynchronous message flow and the underlying decoder structure.   

Pacing Limitations: The TWS API environment enforces strict message rate limits to preserve system stability. The system has a global limit, where high-rate API messages (above 50 per second) can be automatically paced by TWS to the maximum rate, or they may cause disconnection if the pacing limit is exceeded three times. This constraint requires careful design of any system seeking to stream real-time data for a large volume of symbols.  

B. Acquiring Shortable Availability (Quantity)

The primary utility of the TWS API for short selling preparation is the immediate confirmation of liquidity via the reqMktData function. This request is asynchronous and returns data via callback functions.  

    Generic Tick Type 236: To request availability data, the request must include the generic tick type 236.   

Evolution of Data Interpretation: The interpretation of the data returned by Tick 236 has evolved, requiring users to ensure their TWS/IB Gateway installation is current.

    Legacy Interpretation (pre-TWS v974): The tick returned an enumerated value, often described using codes corresponding to colors (GREEN, DARK GREEN, RED) in the TWS watchlist. For example, a value of '3' historically indicated that "there are at least 1000 shares available for a short sale".   

Modern Standard (TWS v974+): Modern implementations (requiring TWS version 974 or higher) now return the precise and explicit data point: the exact number of shares available to short. This transition from an enum status to an exact quantity is fundamentally important for quantitative systems that rely on accurate pre-trade sizing and execution feasibility checks.  

C. The Critical Data Gap: Indicative Borrow Rate Percentage

Despite the TWS API's sophistication in delivering real-time execution metrics, there is a confirmed difficulty in efficiently retrieving the actual indicative borrow rate percentage as a standard, streamable market data field.

The core principle governing the TWS API states that if information is not available in the TWS application itself, it will not be dispatched through the API socket. A review of the available generic tick types used for real-time market data requests confirms that while Tick 236 addresses availability (quantity) , a corresponding dedicated, standard generic tick ID for the indicative rate percentage is notably absent from the general documentation for streaming market data.  

This structural limitation implies that while the TWS API excels at real-time liquidity checks (shares available), it is inefficient or incapable of replacing the FTP as the bulk data source for the actual daily borrow rate percentage. Data related to borrowing rates, such as auction borrow and auction lend rates and sizes, are exposed through highly specific, dedicated data structures intended for the continuous Borrow/Loan market, which are separate from the generic market data stream. To avoid developing highly complex, customized data polling functions within the socket environment merely to retrieve a semi-static rate that updates periodically , the quantitative practitioner must adopt the FTP for rate data.

V. Method 3: Real-Time Snapshot Access via Client Portal Web API (REST)

The Interactive Brokers Client Portal (CP) Web API offers a modern, RESTful alternative to the legacy TWS API. While structurally appealing due to its use of standard HTTP and JSON protocols, this method is severely constrained by architectural dependencies and prohibitive pacing limits, making it impractical for bulk borrow fee retrieval.

A. CP API Architecture and Authentication Overhead

    Protocol: The CP Web API uses standard HTTP verbs and communicates using JSON-formatted messages over secure HTTPS.   

Mandatory Gateway: For individual accounts accessing trading functionalities, authentication is not a simple key exchange. Developers must use the Client Portal Gateway, a separate Java program that acts as a local proxy to route web requests and handle the necessary OAuth 2.0 authentication. This means the CP API cannot be executed as a "pure" command-line process (i.e., a simple curl request) without maintaining a running daemon process locally, similar to the TWS API's requirement for IB Gateway.  

Account Eligibility: Access to this API is limited strictly to active, funded IBKR PRO accounts.  

B. Retrieval Mechanism and Cost

Market data snapshots via the CP API are retrieved using a GET request to the /iserver/marketdata/snapshot endpoint.  

    Field Identification: Data points are requested by passing numerical Field IDs in the URL parameters. While common fields like Last Price (31), Bid (84), and Ask (86) are documented, the specific numerical Field ID corresponding to the indicative borrow rate percentage is generally not published in the easily accessible documentation, indicating a lack of native support for this specialized metric within the standard snapshot API framework.   

Economic Constraint (Snapshot Fee): Unlike streaming API data (which is covered by monthly subscriptions), retrieving a one-time snapshot of current market price or related metrics incurs a transaction fee of 1 cent per snapshot. This immediate per-request cost dramatically increases the overall expenditure for any quantitative system seeking to poll data from a large universe of symbols.  

C. RESTful Pacing Limits and Scalability Failure

The most significant constraint preventing the CP Web API from being a viable solution for bulk data retrieval is its strictly enforced pacing limit.

Interactive Brokers enforces a global request rate limit of 50 requests per second for authenticated users. However, clients utilizing the mandatory Client Portal Gateway—the required authentication tool for accessing brokerage functionality—are restricted to a severely limited rate of 10 requests per second. Violators exceeding this rate face potential 429 "Too Many Requests" status codes and possible temporary IP banning ("penalty box").  

Given that the universe of shortable US stocks exceeds 17,900 listed instruments , attempting to poll this entire universe at 1 cent per snapshot and a maximum speed of 10 requests per second is neither economically practical nor functionally scalable. This severe pacing limit dictates that the CP Web API is functionally limited to low-volume, tactical queries for a handful of symbols, explicitly ruling it out as a candidate for daily exhaustive market scanning for borrow rates.

The analysis confirms that the singular "best way" to access the data involves combining the strengths of the different interfaces. A robust quantitative system must employ a bifurcated strategy:

    Strategic Cost Modeling (Rate %): The system must execute an automated, daily command-line retrieval (using FTP utilities) of the shortstock file. This provides the entire universe of US shortable securities and their current indicative borrow rates, fulfilling the mandate for finding the Rate %. This data is used for strategic decision-making, such as determining position size, target profitability, and identifying high-cost borrow candidates.   

Tactical Liquidity Confirmation (Availability): Immediately prior to placing a short sale order, the system must establish an ephemeral or persistent connection using the TWS API (ibapi) wrapper to execute a reqMktData query using Generic Tick 236. This request is vital for obtaining the precise, real-time quantity of shares currently available.  

C. Causal Relationship between Rate and Liquidity

The efficacy of this hybrid approach is rooted in the causal relationship between the indicative borrow rate and real-time liquidity.

The indicative rate provided by the FTP is generally stable and reflects the long-term cost profile of the security based on current market lending conditions. However, rapid, short-term depletion of available shares can instantaneously alter the risk and feasibility of a short trade. The quantity of shares available is a highly dynamic data point that reflects immediate supply and demand pressures.

A situation where the daily FTP rate is low, but the real-time TWS API Tick 236 indicates a sharp drop in shortable quantity, signals an immediate liquidity crisis. Such a reduction in availability often precedes or accompanies extreme cost increases and elevates the risk of mandatory buy-ins or short squeezes. By fusing the static cost parameter (FTP Rate) with the dynamic availability metric (TWS API quantity), the quantitative system possesses the necessary data inputs to assess both the projected profitability (cost) and the execution risk (liquidity) concurrently, leading to superior tactical trade management.

Conversely, the TWS API, while operationally more complex, remains indispensable for real-time tactical confirmation of share availability via Generic Tick 236.

The fundamental recommendation is the implementation of a dedicated two-part data pipeline:

    Rate Pipeline (Strategic): Automated execution of standard FTP client commands (ftp, open shortstock@ftp2.interactivebrokers.com, get [filename]) daily to ingest the bulk indicative borrow rate data into the quantitative database.   

Availability Pipeline (Tactical): Use of the TWS API (ibapi) wrapper connected to a running IB Gateway/TWS instance for pre-trade, low-latency checks on liquidity (Generic Tick 236).  

This integrated approach ensures the system maintains access to the complete universe of shortable costs without incurring the high operational complexity, pacing limitations, or per-snapshot costs associated with attempting to use either of the API interfaces for comprehensive, bulk rate discovery.

How to Access via Command Line (using curl and tools like jq or pup):

You can fetch this page and parse the HTML table. Here's a conceptual example using curl and a parser:
bash

# 1. Fetch the HTML page
curl -s "https://www.interactivebrokers.com/en/index.php?f=2342" -o stock_yield.html

# 2. Parse it. This requires an HTML parser. Using 'pup' (a command-line HTML parser) as an example:
# Let's assume we want the row for Apple (AAPL)
cat stock_yield.html | pup 'table#table_id json{}' | jq '.[] | .children | .[] | select(.tag=="tr") | .children | .[] | select(.tag=="td") | .text'

Important Caveats:

    Parsing Complexity: The HTML structure can change, so your parser would need to be robust. You'd need to identify the correct table by its ID or class.

    Data Format: The page provides the fee as an annualized interest rate (e.g., 0.5% for easy-to-borrow stocks).

    Limited Universe: This page only lists a subset of stocks, primarily those that are "Easy-to-Borrow" (ETB). It will not show you the exorbitant fees for "Hard-to-Borrow" (HTB) stocks.

Method 2: Using the IB API (ibapi) - Post-Trade & Real-Time

This is the most powerful and direct method, but it provides data after you have a position or have queried a contract.

Data Source: The ibapi (TWS API) provides real-time data points, including the shortable quantity and the approximate borrow rate.

Key ibapi Components:

    reqMktData with Generic Tick Tags: You can subscribe to real-time data and request specific "generic tick tags".

        Tick Tag 101: shortableShares - Indicates the number of shares available for shorting.

        Tick Tag 104: shortableValue - While not the direct fee, this can be related to the cost. The most direct fee indicator is not a standard tick tag.

    reqSecDefOptParams (Security Definition Option Parameters): This method returns a wealth of information about a contract, including stock loan details.

Example Python Code Skeleton using ibapi:
python

from ibapi.client import EClient
from ibapi.wrapper import EWrapper
from ibapi.contract import Contract
import time

class BorrowFeeApp(EWrapper, EClient):
    def __init__(self):
        EClient.__init__(self, self)
        self.nextOrderId = None

    def nextValidId(self, orderId: int):
        super().nextValidId(orderId)
        self.nextOrderId = orderId
        print(f"NextValidId: {orderId}")
        # Now we can make requests
        self.req_borrow_fee()

    def req_borrow_fee(self):
        # Define the contract (e.g., AAPL)
        contract = Contract()
        contract.symbol = "AAPL"
        contract.secType = "STK"
        contract.exchange = "SMART"
        contract.currency = "USD"

        # Request security definition optional parameters
        # This is the key call for pre-trade loan data
        self.reqSecDefOptParams(self.nextOrderId, contract.symbol, "", contract.secType, contract.conId)

    def securityDefinitionOptionParameter(self, reqId: int, exchange: str, underlyingConId: int, tradingClass: str, multiplier: str, expirations: set, strikes: set):
        # This callback returns a lot of data, but for stocks, the borrow fee info is NOT here.
        # This is more for options. We need a different approach.
        print(f"SecDefOptParam. ReqId: {reqId}, Exchange: {exchange}, TradingClass: {tradingClass}")

    # A more practical approach is to check the data after making a real-time data request.
    def tickGeneric(self, reqId, tickType, value):
        # TickType (number) to String mapping:
        # 101: shortableShares
        if tickType == 101:
            print(f"Shortable Shares: {value}")
        # There isn't a direct 'borrow fee' tick type. The fee is often found in account values.

    def error(self, reqId, errorCode, errorString):
        print(f"Error. Id: {reqId}, Code: {errorCode}, Msg: {errorString}")

def main():
    app = BorrowFeeApp()
    app.connect("127.0.0.1", 7497, clientId=123) # 7497 for TWS, 4001 for Gateway

    # Run the socket in a separate thread
    import threading
    api_thread = threading.Thread(target=app.run, daemon=True)
    api_thread.start()

    # Keep the script running
    time.sleep(10)
    app.disconnect()

if __name__ == "__main__":
    main()

The Reality of ibapi for Borrow Fees:
The borrow fee is often not a single, easily accessible real-time data point in the API. The most reliable way to get it programmatically is often to:

    Place a small, paper trade short order for 100 shares.

    In the order confirmation dialog before transmitting, IBKR will display the estimated annualized borrow fee.

    Cancel the order. This is a manual process and hard to automate reliably.

Method 3: Account Window Query (Post-Trade)

If you already have a short position, the data is readily available in your account.

Data Source: The ibapi method reqAccountSummary or by parsing the account updates.

How it works:
Once you are short a stock, IBKR will send you daily account updates that include a line item for the stock loan fee. You can calculate the effective annual rate from this.

Summary & Recommendation
Method	Best For	Accessibility via CLI/API	Pros	Cons
1. Stock Yield Page	Pre-trade screening of ETB stocks.	Good (Web Scraping)	Structured data, no IBKR connection needed.	Limited to ETB stocks, HTML structure can change.
2. IB API (ibapi)	Real-time data & integration into trading systems.	Excellent (Direct API)	Real-time, programmable, most accurate for your account.	Complex; borrow fee is not a single, straightforward field.
3. Account Query	Post-trade analysis and monitoring.	Good (Direct API)	Accurate reflection of actual costs incurred.	Only works after you have already taken the position.

Best Practical Approach:

For a command-line tool, your most robust method is a hybrid approach:

    Primary Source: Create a script that scrapes the official IBKR Stock Yield page (https://www.interactivebrokers.com/en/index.php?f=2342). Use a robust parser like beautifulsoup4 in Python or pup in bash. This covers most of your needs for liquid, ETB stocks.

    Fallback for HTB Stocks: For stocks not on that list, you must assume they are HTB. The only way to get the exact fee is through the ibapi by attempting a pre-trade check (which is complex) or by checking the "Stock Loan" tab in TWS/Client Portal manually. There is no simple, free, public feed for HTB borrow rates from IBKR.

Example Command-Line Tool Workflow:
bash

# Try to get the rate from the cached/downloaded Stock Yield page
